# §25 — Media store and retention

> **Confidence:** `DURABLE`
> The encryption property (§25.1) and the retention position (§25.6) are
> durable. Storage backend and limits are revisable.

---

## 25.1 What the media repository actually holds

The single most important property, and the one that makes every other decision
in this chapter easy:

**Every file uploaded from an encrypted room is encrypted by the client before
upload.** The homeserver receives a blob of AES-CTR ciphertext and a filename it
did not choose. The decryption key travels in the event body, which is itself
Megolm-encrypted (§5.3.2) and which the server cannot read.

So the media store is a bag of opaque bytes. The operator cannot view a user's
photo, cannot thumbnail it server-side, cannot scan it, and cannot be compelled
to produce it in readable form (§3.3, A5).

Two consequences that follow immediately:

- **`dynamic_thumbnails` must be off** (§22.4). The server cannot thumbnail
  ciphertext. Clients generate their own (§12.6.2).
- **Content scanning is impossible.** This is a real regulatory tension, not a
  technicality, and §31.4 addresses it head-on rather than pretending otherwise.

## 25.2 Size limits

| Limit | Value | Source |
|---|---|---|
| `max_upload_size` | **100 MB** | Cloudflare's request cap on the tunnel. Not a product choice. |
| Client-side cap | 95 MB | Fail in the client with a clear message, not at the edge with a 413 |
| Image auto-downscale | > 4 MB | §14.5.3 |
| Video | Transcode or reject over the cap | §14.5.3 |

The 100 MB figure comes from the same place Nextcloud's `max_chunk_size` of
50 MB on this box does: Cloudflare free-tier request limits. It is an edge
constraint that propagates all the way into the client's upload UI, and it is
better to discover it at design time than as an unexplained failure on a 200 MB
video.

**Chunked upload is not available** — the Matrix media API is a single request.
So the cap is hard, and the client must enforce it early, before the user has
waited through a compression pass.

## 25.3 Backend: filesystem, not object storage

| | Filesystem on `Pool1-MAIN` | S3-compatible |
|---|---|---|
| Setup | Nothing — it is a path | Provider, bucket, credentials, a Synapse media storage provider |
| Backup | Included in the existing replication | Separate arrangement |
| Cost | Already paid | Per-GB plus egress |
| Scale ceiling | ~1.5 TB free today | Effectively unbounded |
| Deletion semantics | Obvious | §5.9 flags this as needing verification |

**Decision: filesystem, at `Pool1-MAIN/social/media`.**

There is 1.5 TB free on a replicated pool that the operator already runs. Adding
an object store means adding a provider, a credential, an egress bill and a
deletion-semantics question that this project's own protocol chapter lists as
unverified. None of that buys anything until the pool is actually the
constraint, and §28 says it will not be for a long time.

**Reversal cost: low.** Synapse supports media storage providers that migrate
files out to object storage transparently. The trigger to do it is the dataset
quota (§25.5) being approached, not a feeling that object storage is more
professional.

## 25.4 URL previews stay off

`url_preview_enabled: false`, and this deserves more than a config line.

A URL preview is generated by **the homeserver fetching the link**. In an
encrypted room the client sends the URL to the server to be previewed — which
means the server learns a piece of message content it is otherwise structurally
unable to see, and makes an outbound request that tells a third-party site that
someone on this homeserver is reading their page.

§9.6.1's acceptance screen tells users, in two columns, exactly what the
operator can and cannot see. "The content of your messages" is in the *cannot*
column. Enabling URL previews would make that false for a category of message
content.

Turned off in both places (§20.3 and §22.4) because either alone is one
configuration mistake away from a disclosure the product has promised does not
happen.

Clients may generate previews locally, fetching the URL themselves. That is a
different privacy trade — the *user's* IP reaches the site, not the server's —
and it is the user's to make. Default off; if offered later, offered explicitly.

## 25.5 Quota

Set at dataset creation, not after:

```bash
sudo midclt call pool.dataset.create '{
  "name": "Pool1-MAIN/social/media",
  "type": "FILESYSTEM",
  "compression": "OFF",
  "quota": 214748364800
}'
```

200 GB to start. Two deliberate choices:

- **`compression: OFF`.** The contents are ciphertext (§25.1). LZ4 on random
  bytes burns CPU to achieve nothing. This is the one dataset on the pool where
  compression is actively wrong.
- **A quota exists at all.** §21.8 lists "the media store fills `Pool1-MAIN`" as
  a blast-radius risk to a pool that also holds a point-of-sale database, three
  customer websites and a Nextcloud with real user data. A quota converts that
  from an outage into an error message.

**Synapse's behaviour on a full media store must be verified** during phase 1.
The desired behaviour is that uploads fail cleanly and messaging continues. An
alert fires at 80% (§27.3).

## 25.6 Retention

`retention.enabled: false` in `homeserver.yaml`, deliberately, and this is the
chapter's most contestable position.

**The argument for leaving it off:**

- The device is the primary copy (§12.2). Server-side purging does not free the
  user's disk and does not change what they can read.
- Purging events the operator cannot decrypt provides no privacy benefit — the
  server never had the content.
- It breaks new-device history restore (§8.5): a device signing in after a purge
  cannot fetch what was removed, and the user experiences it as history
  vanishing for no reason.
- It is a background job that touches the database continuously, on a box shared
  with production services (§21.8).

**The argument against**, recorded honestly because it will be raised: data
minimisation under GDPR (§4.3.2) prefers not keeping personal data indefinitely,
and encrypted events plus their metadata are personal data even when unreadable.

**The resolution:** retention of *content* is not where the privacy win is,
because there is no readable content. The win is in metadata, and that is
bounded separately:

| Setting | Value | What it bounds |
|---|---|---|
| `user_ips_max_age` | 28d | IP and user-agent logs — **genuinely readable personal data** (§32.4) |
| `redaction_retention_period` | 7d | How long the pre-redaction original lingers |
| `forgotten_room_retention_period` | 28d | Cleanup of rooms everyone has left |
| Media | See §25.7 | |

`user_ips_max_age` is the one that matters. It is the only setting in this
chapter that limits retention of something the operator can actually read about
a user, and it is the one a data protection authority would ask about.

Revisit `retention.enabled` when disk is the constraint or when a specific legal
obligation requires it. Not before, and record the reasoning when it changes.

## 25.7 Media deletion

Media is not deleted when a message is. Three separate mechanisms, none
automatic:

| Trigger | Mechanism |
|---|---|
| Account deleted (§7.6) | Admin API purges that user's media. **Must be part of the deletion procedure** (§32.3) or deletion is incomplete and the §4.3.2 obligation is unmet. |
| Message redacted | Media persists. The admin API can purge it; not wired up by default. |
| Orphaned media | Admin API supports deleting media not referenced by any event, and by age |
| Quota pressure | Operator action, with a runbook (§29.5) |

**The account-deletion row is a compliance obligation, not a housekeeping
preference.** A user who deletes their account and whose uploaded files remain
on the server has not had their data erased. §32.3 makes media purge an explicit
step with an explicit verification.

### 25.7.1 The remote-media exception that does not apply

Synapse ordinarily caches media from other servers and purges it aggressively.
With federation off (§2.6) there is no remote media, so that entire mechanism is
inert here. Mentioned only so nobody tunes it expecting an effect.

## 25.8 What clients must do

Because the server does so little, the client carries the load:

| Responsibility | Section |
|---|---|
| Encrypt before upload | §5.3, mandatory |
| Downscale images before upload | §14.5.3 |
| Generate thumbnails locally | §12.6.2 |
| Cache decrypted media outside app-visible storage | §12.6.1 — the plaintext problem |
| Evict cache under pressure | §12.6.3 |
| Enforce the size cap before compressing | §25.2 |

§12.6.1's plaintext problem is the one with teeth: decrypted media on disk is
the one place message content exists in the clear on the device, and it must not
land anywhere another app or a backup can read.

## 25.9 Open questions

- **Does a full media store fail cleanly?** Phase 1 verification (§25.5). The
  bad outcome is Synapse erroring on every request rather than just uploads.
- **Is 200 GB right?** It is a guess scaled from §28's assumptions. The number
  matters less than the alert at 80% and the runbook for raising it.
- **Should there be a per-user media quota?** Synapse has no native one. A
  single user could consume the whole dataset. The invite tree (§9.4) makes that
  an accountable act by a known person rather than an anonymous one, which is
  probably sufficient at this scale — but it is a real gap, and the mitigation
  is social rather than technical.
